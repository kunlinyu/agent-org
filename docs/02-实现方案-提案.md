## 1. 目标与非目标

沿用需求说明书第 1 节，不重复。本文的设计目标只有一条可检验的表述：

> 用**尽量少的自研代码**，把 DSH 的会话/子代理/任务板/定时/投影能力，装配成一个**规则可执行**（而非提示词自觉）的单人组织。

非目标（明确排除，防止范围蔓延）：自建 agent 运行时、自建 Web 看板、fork DSH、多项目并行、多租户。

本节是实现的地基。**每条都标注了依据**；标注「待验证」的不得在实现中当作结论使用。

### 2.2 结论：能力边界三分法

| 需求域 | DSH 直接承担 | 本框架补充 |
|---|---|---|
| 组织与会话 | 持续子 Session、消息路由、打断、树内发现、子会话 UI | 确定性编制、角色权限、执行者生命周期 |
| 任务协作 | Team 的 owner/依赖/CAS/`writeScopes` | 业务状态、任务卡片、spec 与合入门禁 |
| 用户请示 | 事件日志、会话续接、slot 扩展 | 结构化请示协议、全局待办、回复关联、未读与等待时长 |
| 代码隔离 | worktree 服务、工作目录、沙箱策略 | 槽位自动建删、Git 授权、spec 前置门禁 |
| 模型分档 | `agentPreset`、模型选择、token 计量 | T1–T4 规则、升档校验、价格表 |
| 业务监控 | `running`/`inactive`、Projection 机制 | `blocked`/`waitingUser`/`done` |
| 定时巡检 | Cordis 宿主侧 timer | 向指定子角色投递巡检 |

**核心原则：原生机制负责"能不能通信"，领域层负责"组织上允不允许"。**

## 3. 总体架构

```
┌──────────────────────────────────────────────────────────────┐
│ L3 表现层   org-client（client 插件）                          │
│   ·「待我裁决」面板：条数 / 最久等待 / 按 agent 一行            │
│   · 监控条：全面暂停、静默、成本卡                             │
│   · 复用原生：会话视图、ui-subagent 跳转、Team 任务板           │
├──────────────────────────────────────────────────────────────┤
│ L2 编排层   org-core（Host 插件）                              │
│   · org-runtime：启动期确定性建树 + 容量预算 + 槽位生命周期      │
│   · org-* 强化工具：派活 / 建执行者 / spec / 请示 / 汇报        │
│   · 事件与投影：orgRequests / orgBusiness / orgCost            │
│   · 门禁：tools/pre-execute（spec 未批禁写码、禁强推主干）       │
│   · 巡检时钟、暂停协调（Q2 待定）、成本聚合                     │
├──────────────────────────────────────────────────────────────┤
│ L1 组合层   org-presets（bundle，纯 YAML，10 个角色组合）       │
├──────────────────────────────────────────────────────────────┤
│ L0 底座     会话日志(唯一真相) · Team 任务板(实时协调)           │
│             项目仓库 git(长期事实) · 团队规范仓库 git(规范)      │
│             槽位 worktree(代码隔离) · DSH 版本锁定 + 契约测试    │
└──────────────────────────────────────────────────────────────┘
```

装配为**两个 bundle 三个包**：

| 包 | 类型 | 职责 | 安装方式 |
|---|---|---|---|
| `@local/org-presets` | 纯 YAML bundle | 10 个角色 preset 声明 | `plugin_manager install_bundle` |
| `@local/org-core` | Host 插件 | 领域服务、工具、投影、门禁、时钟 | 同上（同一 bundle 的可选依赖） |
| `@local/org-client` | Client 插件 | 收件箱面板、监控条、裁决交互 | 同上 |

> 一个 bundle 可同时含 Host 与 Client 面，故也可并作一个包；拆开是为了让"改 UI 不重启 Host"。

## 4. 组织编制与生命周期

### 4.1 编制必须由代码建立，不由提示词决定

**决定：`org-runtime` 在根会话激活时幂等执行 `ensureRoster()`，不依赖 HRD 模型自行建树。**

理由（采纳来源 B）：模型会漏建、重名、认错上下级；而 ORG-4 要求"直系上级由创建关系决定"——创建关系必须由代码写。

```
ensureRoster(rootAgent):
  1. 读取编制文件 org/layout.yml（见 4.2）
  2. 查 subagentCatalog → 对缺失角色按 preset 顺序 spawn（name=槽位实例名，agentPreset=角色 preset）
  3. 建立角色→SessionId 映射，写 org/roster 事件（log-only）
  4. 校验：深度 ≤2、每棵树 activation 数 ≤ 预算、名字未占用
  5. 任一失败 → 本轮 HRD 首轮被拦截并提示具体缺口（不静默半成品）
```

**待验证 V1**：根会话激活时可供插件挂钩的确切 seam（`agent/created` / 会话打开的精确时机）；若不存在稳定 seam，退化为"HRD 首轮 `agent/pre-step` 前置检查"。

### 4.2 编制表（org/layout.yml 的语义，字段为实现契约）

| 槽位 id | 角色 | 直系上级 | preset | 深度 | 常驻 |
|---|---|---|---|---|---|
| `lead` | HRD | — | standard + org 注入 | 0 | 是 |
| `rd` | 研发总监 | lead | `org-rd-director` | 1 | 是 |
| `pmo` | 项目经理 | lead | `org-project-manager` | 1 | 是 |
| `prd` | 产品经理 | lead | `org-product-manager` | 1 | 是 |
| `qa-rule` | 规范检察员 | lead | `org-compliance` | 1 | 是 |
| `hr` | HR | lead | `org-hr` | 1 | 是 |
| `arch` | 架构师 | rd | `org-architect` | 2 | 待定 Q4 |
| `exec-1..3` | 执行者 ×3 | rd | `org-executor` | 2 | 按任务创建/销毁 |
| `verify` | 校验者 | rd | `org-verifier` | 2 | 待定 Q4 |
| `tester` | 运行测试员 | rd | `org-test-runner` | 2 | 待定 Q4 |
| （discussion） | 深谈 fork | 见 Q3 | `org-discussion` | 按 Q3 | 临时 |

### 4.3 逻辑槽位 vs 实例名（采纳来源 B）

**决定：DSH 的 agent 名是消耗品，不能用作槽位标识。**

- 逻辑槽位：`exec-1`（只出现在 UI、事件、任务卡片中，是稳定引用）
- 实例名：`exec-1-20261121t1015`（≤32 字符、同父唯一、创建后不可改）
- 路由：一律用**实例名或 SessionId**；槽位 id 只做展示与归属聚合。
- 槽位释放：会话以 `org/slot-released` 标记，实例名不回收。

**推论**：任何"同一个名字反复重建"的设计都会在第 N 次撞名失败。常驻角色（`rd`/`pmo`/…）也在项目内首次创建时得到带时间戳的实例名。

### 4.4 容量预算（本方案最硬的数字约束）

`maxActiveSubagents` 是**每棵树共享**、**计数驻留 activation**、**超限硬失败**（F5）。据此算账：

| 场景 | 树内 activation | 对 16 的余量 |
|---|---|---|
| 全常驻编制（lead + 5 负责人 + 6 下属） | 12 | 4 |
| + 1 个修复执行者 + 1 个深谈 fork（若同树） | 14 | 2 |
| + 并发任务再建 2 个执行者 | 16 | **0（再要就报错）** |

**决定**：编制**不全常驻**（Q4 推荐值 `arch`/`verify`/`tester` 按里程碑创建、用完销毁），并把 `maxActiveSubagents` 调到 **24**（Q5）。

> 注：普通 Session fork 会成为**独立树**，各自拥有独立容量池，因此不占主树名额——这是 Q3 取舍的一个隐性成本项。

### 4.5 深度校验

`maxDepth=2` → 执行者（深度 2）不能再派活。因此 **DEV-18「失败不原地修，新建修复执行者」在结构上只能由研发总监执行**，与需求天然一致。若将来把执行者提到深度 1，须同步改 CON-1。

## 5. 强化工具层：规则写在工具里，不写在提示词里

**决定：不向角色暴露原生派活/消息工具，改为 `org_*` 包装；权限校验在工具执行时进行。**

| 工具 | 可调用者 | 作用 | 关键校验 |
|---|---|---|---|
| `org_assign_task` | rd；pmo 仅可写排期字段 | 建任务、改派、改依赖 | 改派权只在 root（ORG-7）；pmo 不得发明优先级（DEV-3） |
| `org_spawn_executor` | rd | 建 worktree + spawn 执行者 | 深度=2、容量余量、槽位空闲、preset 固定 |
| `org_release_executor` | rd | 合入确认后销毁实例 | 必须先有 `org/merge-confirmed`（DEV-16） |
| `org_submit_spec` | 执行者 | 写 spec 到指定路径 + 登记 | 任务必须属于自己；写码门禁解锁的唯一前置 |
| `org_review_spec` | rd | 批准/驳回 spec | 只有该任务的直系上级 |
| `org_request_user` | 任意成员 | 发起请示（第 6 节格式） | 格式、单问题、不可逆必须 `blocking`（CNS-4） |
| `org_report_parent` | 任意成员 | 任务级反馈给直系上级 | 目标必须 = 创建者（COM-2） |
| `org_update_task` | 任务 owner | 推进业务状态 | 只能操作自己拥有的任务 |
| `org_status` | 任意 | 只读：树、槽位、待办、暂停态 | 只读 |
| `org_cost_report` | hr、root | 成本汇总（token + 价格表） | 只读 |
| `org_pause` / `org_resume` | root | 停机/恢复 | **Q2 未定，先不实现** |

**保留给角色的原生工具**：只读类（`read`/`glob`/`grep`/`lsp`/`web_*`）、执行类（`bash`/`pwsh`，受 5.1 门禁）、`list_agents`（只读发现）、`skill`、`todo_write`。

**收回的原生工具**：`subagent` / `subagent_fork`（仅 rd 可用，且必须走 `org_spawn_executor`）、`send_message`（改为 `org_report_parent` / `org_request_user`）、`interrupt_agent`（仅祖先，仍保留给 rd 与 root，因为"打断"本身是 ORG-5 的权限，不该被领域层再包一层）。

### 5.1 spec 前置门禁（硬门禁，采纳来源 B）

**决定：spec 未经批准前，用 `tools/pre-execute` waterfall 拒绝写操作，而不是靠模型自觉。**

| 阶段 | 允许 | 拒绝 |
|---|---|---|
| spec 未提交 / 未批准 | `read`/`glob`/`grep`/`list_agents`/只读 bash | `write`、`edit`、`str-replace`、写类 bash/pwsh |
| spec 已批准 | 编码工具全开 | 强推主干、改 CI、提交密钥（SEC-3） |
| 本地自测通过 | 推送分支、请求评审 | 直接合入主干 |

**待验证 V2**：`bash`/`pwsh` 的"只读判定"是否可靠（重定向、`git commit`、子进程写入都属于写）。若不成立，改为"spec 未批 → 干脆禁用 shell，只给读文件工具"，用严格性换可判定性。

## 6. 请示协议（唯一必须自研的核心）

### 6.1 为什么必须自研

`ask_user_question` 对 delegated 子 agent 直接拒绝（F7），而 COM-4 要求"所有 agent 都可直接向我请示，不经上级转发"。所以请示必须是一条**自己的**事件通道。

### 6.2 事件契约（写入组织树根 Session 日志）

| 事件 | 载荷 | 写入者 |
|---|---|---|
| `org/request` | `requestId`、`originSessionId`、`originSlot`、`taskId?`、`summary`、`options[]`、`recommendation`、`reversible`、`source`、`blocking`、`createdAt` | `org_request_user` |
| `org/answer` | `requestId`、`answer`、`answeredAt`、`by` | 用户裁决动作 |
| `org/cancel` | `requestId`、`reason` | 发起者或 root |
| `org/read-cursor` | `sessionId`、`lastReadSeq`、`updatedAt` | 用户阅读动作 |

**决定：事件落根日志**（采纳来源 B，覆盖来源 A 的"写发起者日志"）。理由：
1. 只需订阅一条日志即可派生全组织待办，不必同时 observe 十几个会话；
2. 插件自有事件是 log-only（F11），不会污染 root 的模型上下文；
3. 根日志的生命周期长于任何子会话，子会话归档后待办不会凭空消失。

**待验证 V3**：插件向自己不是发起者的 Session 追加事件的写入权限与投影订阅方式。

### 6.3 状态全部派生，不建第二份存储

```
pending(request)  = 有 org/request，且无对应 org/answer 与 org/cancel
waiting(request)  = pending && (blocking || 不可逆 || 花钱)
unread(session)   = 该会话最后相关事件 seq > read-cursor
waitMs(request)   = now - createdAt
```

**决定：收件箱是投影，不是数据库。** 与需求 2.3 的"不维护第二份状态副本"一致。

### 6.4 展示与回流（COM-7~COM-14）

| 环节 | 实现 |
|---|---|
| 面板位置 | `sidebar.panellist` 注册「待我裁决」：总数 + 最久等待（EX-7） |
| 每 agent 一行 | 行 = 槽位；带未读/待裁决徽标；有多个待办时折叠 |
| 点击进线程 | 复用 `ui-subagent` 打开 `originSessionId`（不自建会话视图） |
| 快速回答 | 面板内按钮 → 写 `org/answer` → `subagents/prompt` 投回原会话 |
| 深谈 | 见 Q3；不论哪种形态，**只回填结论**（COM-10） |
| 幂等 | 只有 `pending` 的 `requestId` 可被回答；重复点击返回已答（防重复唤醒） |
| 不做的事 | **不解析自然语言判断"这句是不是回答"**：只有明确回答动作才关闭请示 |

**为什么 `subagents/prompt` 而不是 `send_message`**：前者是 Host 侧 Remote，用户身份投递、可校验目标会话权限；后者要求"存活的发送方 agent"，用户不是树成员。

## 7. 两套状态语义必须分开

| 语义 | 来源 | 取值 | 消费者 |
|---|---|---|---|
| **引擎态** | DSH `list_agents` / `agent/status` | `running` / `inactive`（+ `unsupported` 等诊断） | 容量调度、巡检判断"是否真在跑" |
| **业务态** | 本框架投影 | `todo` / `doing` / `blocked` / `waitingUser` / `reviewing` / `done` | 收件箱、看板、汇报 |

**禁止**把 `running` 当"在干活"、把 `inactive` 当"完成了"（DSH 文档明确 `running` 只表示 driver 正在抽空队列）。业务态一律由 `org/*` 事件派生。

## 8. 任务板与 Git 的事实边界（只存一份，各有唯一写入者）

| 事实 | 唯一写入者 | 存放 | 说明 |
|---|---|---|---|
| owner / claim / revision / 依赖 / `writeScopes` / 临时协调态 | Agent Team | 根 Session 日志 | 实时性优先，CAS 防覆盖 |
| 完整任务卡片（ID/目标/验收/子目录/依赖/规则/规范片段/现状摘要） | 项目仓库 git | `tasks/<taskId>.md` | 自包含（CTX-4），卡由 `org_assign_task` 落地 |
| spec 与审批记录 | 项目仓库 git | `tasks/<taskId>/spec.md` + 审核事件 | 修复杂凑四样之一（CTX-7） |
| 测试 / 验收 / 校验 / 规范判定报告 | 项目仓库 git | `reports/` | 邮件只放摘要 + 链接（ACC-5） |
| 项目内共识、进度 | 项目仓库 git | `rules/`、`progress.md` | CNS-7 默认项目内 |
| 团队规范、编码/依赖/安全基线 | 团队规范仓库 git | `baselines/` | 沉淀需 `org_review_spec` 式放行 |
| 组织事件（请示/审批/暂停） | 根 Session 日志 | — | 不进 git，避免双写 |

**规则**：同一个事实不允许同时在 Team 和 git 各存一份完整状态。`taskId` 是唯一贯穿键。

## 9. 代码隔离与合入

### 9.1 槽位

```
项目仓库/            ← 主会话工作区，也是唯一 push 目标
├── .worktrees/
│   ├── exec-1/      ← 槽位 1（独立分支 slot/exec-1-<taskId>）
│   ├── exec-2/
│   └── exec-3/
```

1. `org_spawn_executor` 用 `git worktree add` 建槽位（分支名含 taskId）；
2. spawn 时把执行者 `cwd` 指到槽位目录（`subagent` 的 `cwd` 选项）；
3. 执行者不持有 worktree 类工具，不自行切换目录；
4. 槽位空闲时 `git worktree remove` + `git fetch && rebase` 重置到主干（DEV-8）；
5. 实例销毁后保留目录以便复用（DEV-8），但分支名按任务重建。

### 9.2 待验证 V4（最高优先）

**linked worktree 的 `.git` 写授权**：提交要写主仓库的 `.git/worktrees/<name>/`，该路径在 workspace-write 沙箱下通常位于工作区之外，可能被拒。三条候选路径：

| 方案 | 说明 | 风险 |
|---|---|---|
| a. 放行项目仓库 `.git` 目录 | 由宿主统一处理授权 | 放宽 SEC-1 |
| b. 整目录副本（`git clone`）而非 worktree | 每槽位自带 `.git`，沙箱天然覆盖 | 磁盘与 fetch 成本；DEV-7 措辞是"独立代码拷贝"，副本更贴合 |
| c. 用 DSH 实验性 worktree 服务 | 它自称在调用者沙箱策略下处理共享 Git 元数据 | 会把调用者会话 cwd 切走；仍是实验能力 |

**默认路径 a，失败即降级 b。**

### 9.3 合入与验证（DEV-13~18）

```
本地自测 → push 分支 → rd 评审（冲突简单自解，复杂打回）
→ 合入主干（写 org/merge-confirmed）→ 销毁执行者实例（DEV-16）
→ 正式测试 → 校验 → 规范判定
→ 正式测试失败：冻结 feature 合入、fix 通道保持开通；新建修复执行者（四样上下文）
```

**未验证的降级**：若"推送+评审"在单人本地仓库上没有真实远端，则评审退化为本地分支 merge + `org/merge-confirmed` 事件，流程语义不变。

## 10. 巡检、冷却与"全面暂停"

### 10.1 巡检（EX-5/EX-6）

原生 `schedule` 不能指向 delegated 子会话（F8），故：

```
org-core 内的宿主侧 timer（每 30 分钟）
  → 找到 pmo 的实例
  → send_message(pmo, "巡检：重排任务、语义合并、判定冷却")
  → pmo 产出结论写 org/* 事件
```

全面暂停后只允许**一次**巡检（延迟 10 分钟）；重排后仍全面暂停 → 彻底静默，只展示待办数与最久等待。

### 10.2 「全面暂停」的语义——**待定 Q2**

| 选项 | 语义 | 对需求的影响 |
|---|---|---|
| A（守需求 2.3） | 纯派生值：没有任何 agent 在 running。**不提供停机动作** | 不改需求；但演示"暂停后巡检"需要人为制造静止 |
| B（来源 B） | 主动停机：`org_pause` → 宿主中断所有活跃成员 → 派生 `pausing` → 一次巡检 → `paused` | 引入需求未描述的动作，须在 00 记决策覆盖 2.3 |

本文**不预设立场**，两种都留接口；实现阶段按 Q2 的结论二选一。

## 11. 模型分档与成本（MOD-1~3、OPS-4）

| 项 | 方案 |
|---|---|
| 档位默认值 | 写在各角色 preset 里（T1–T4），创建执行者时由 `agentOptions` 落到模型路由 |
| 计算 | `clamp(基础档 + 全局平移 + 执行者自提, 1, 4)`；自提只能 +1，不可降（MOD-3） |
| 升档校验 | 由 `org_spawn_executor`/领域工具校验，执行者不得自选昂贵模型 |
| 价格表 | 团队规范仓库 `prices.yml`（provider/model/单价），因为 DSH 无货币成本 API（F14） |
| 上下文阈值 | 50% 只能用 DSH 的估算值（`tokenUsage`/`contextPressure`），并注明非精确 |
| 收尾策略 | 不指望模型自觉省上下文：接近阈值由宿主提示执行者收尾并释放 |
| 口径声明 | 成本为**估算参考值**，不是账单 |

**Q8**：当前 `allowedModels` 只有 `deepseek-flash`，T1–T4 无法真正分档。要么先只做"档位标注"（不落模型），要么先补模型路由。

## 12. 规范沉淀与注入（CNS-* / KN-*）

这一环是"打扰自然变稀"和 AC-4/AC-7 的实际载体，**来源 B 的方案未覆盖，本文补全**。

```
触发（CNS-1/2/3：同类第 2 次、与已有共识冲突、出现"以后都…"）
  → 强谈或请示（CNS-2 冲突时必须展开，不允许快速点掉）
  → 规则卡片写入项目仓库 rules/<cardId>.md（编号/作用域/日期/来源）
  → 项目结束或经放行后沉淀到团队规范仓库（CNS-7、KN-3）
  → 新项目/新任务启动时按「角色 + 任务涉及子目录」切片注入
```

**注入机制**：org-core 在 `systemPrompt.section()` 里按会话解析出"该角色的规范切片"，而不是全量塞入。全量注入会随规范增长线性吃掉上下文，与 CTX-5 的 ≤50% 预算冲突（**Q10**）。

另外：规范检察员的判定标准必须来自团队规范仓库的**版本化文件**（KN-4），所以它的 preset 只读该仓库，不读项目内临时约定。

## 16. 实施顺序：先打通一条纵向闭环

### 阶段一：证明核心机制可行（先不做全部角色/UI）

链路：**HRD → 研发总监 → 1 个执行者 → 校验者**，同时包含：

1. 确定性建树（只建 3 个角色）
2. 一条结构化请示 + 用户回复（`org_request_user` → 面板 → 回流唤醒）
3. spec 门禁（未批拒绝写码）
4. 一个独立 worktree 槽位（V4）
5. 自测 → 合入 → 正式测试 → 校验
6. 执行者一次性释放
7. 全面暂停（按 Q2 结论的形态）

> 这一步能暴露绝大多数架构问题；**在它跑通之前不铺开其他角色**。

### 阶段二：扩展协调能力

多执行者与依赖、Team 完整接入、业务态投影、未读/等待时长、T1–T4 与成本、定时巡检与暂停后巡检、规范切片注入。

### 阶段三：补增强能力

深谈 fork（Q3）、邮件等外部通知（Q9）、备份恢复、跨项目复用。
