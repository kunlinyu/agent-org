# 构想过程：从一个模糊想法到需求基线

> 本文记录这套框架**为什么长成这样**，而不是记录它长成什么样。
> 需求本身见 [01-需求说明书.md](01-需求说明书.md)。
> 日期：2026-11-20

---

## 1. 起点

最初只有一句话：

> 我有一个 AI 编程方面的模糊想法，希望把整个想法描述清楚。

第一个具体形态出现在第三轮对话：

- 只有我一个人用
- 载体是 DSH + 一组插件
- 被开发的项目各式各样
- 目标：多 agent 架构要和我**密切沟通**，在充分沟通的前提下**连续数天不跑偏**
- 我的角色：**像一家公司的老板**

这句话后来几乎没变过，但每一个词的解释都变过。

## 2. 被否掉的建模

这一段是最有价值的部分——**这些方案当初都看起来合理**。

### 2.1 被否：把「打扰」当成本

**当时的想法**：老板的注意力最贵，"密切沟通"不能等于"频繁打扰"，所以要给收件箱设准入闸门、限流、按风险分级。

**为什么被否**：

> "前期我特别愿意被淹没，我对项目的进展控制非常强迫。"
> "打扰不是成本，是控制手段。"

于是"闸门"这个设计被撤掉，只保留一个不同目的的分类：**区分"阻塞在你"和"仅汇报"**——不是为了减量，是为了让我知道谁在等我。

**留下的教训**：不要替用户假设他的偏好。同一个机制，动机不同，设计就不同。

### 2.2 被否：阶段机是全局状态机

**当时的想法**：项目有阶段（需求→预研→生产→验收→维护），建模成一个全局状态机，界面显示当前阶段枚举。

**为什么被否**：

> "阶段机不是一个显示的状态机，是根据项目经理的知识动态调整的，不用精确建模，更偏向描述性建模。"
> "我们不假设项目总是瀑布模型，实际上不同的需求应该各有这个流程。"

于是改成：**阶段挂在每条需求上**，产品经理判定，项目经理只产出一句**描述性的话**。界面上显示描述，不显示枚举。

**留下的教训**：真实组织里大量状态是"描述"而非"状态机"。硬建模会制造不存在的约束。

### 2.3 被否：运行状态机独立维护

**当时的想法**：维护一个全局运行状态（active / stalled / waiting / halted）。

**为什么被否**：

> "运行状态机并不需要独立维护，这是对所有 agent 的运行状态的一个总结，实际上只需要维护具体每个 agent 的运行状态即可。"

于是「全面暂停」变成**派生值**：没有任何 agent 在 running。这与 DSH「会话日志是唯一真相」的原则天然一致，也避免了第二份会漂移的状态副本。

### 2.4 被否：交接单

**当时的想法**：长任务一定撑爆上下文，所以上下文接近上限时生成一份交接单，靠它重建角色。

**为什么被否**：

> "任务拆解应该尽量让一个完整的任务在上下文以内完成，即使可能超出，也应该在一次上下文压缩以后就能完成，如果还不能，就应该触发 HR 的汇报。"

于是约束**前移**：不是事后补救，而是**拆解时就把任务切到能装下**。执行者改为一次性实例，任务结束即销毁，跨任务累积问题直接消失。

**留下的教训**：事后兜底不如事前约束。能改粒度的，就不要加补丁。

### 2.5 被否：资源锁

**当时的想法**：三个执行者并行改同一份代码必然冲突，所以用目录级锁，TTL 1 分钟，研发总监管锁。

**为什么被否**（用户自己提出了更好的方案）：

> "每个执行者槽位应该由完全独立的代码拷贝，然后向我本地部署的代码仓库做推送，并交给研发总监来做评审和合入。"

于是并发从"加锁"变成"**物理隔离**"：worktree + 推送 + 评审合入。锁被彻底删除，只留一个弱化的"子目录任务声明"用于防重复劳动。

**留下的教训**：遇到资源争用，先问"能不能不共享"，再问"怎么共享得更好"。物理隔离通常比协议更便宜。

### 2.6 被纠正的理解：收件箱 ≠ DSH 的 todo 列表

**当时的想法**：DSH 已有全局 todo 收件箱（`inbox_add / list / update / done`），复用它，补一个回复通道即可。

**为什么错**：

> "我说的收件箱不是你说的收件箱……我说的收件箱只用来让我和每个 agent 交流沟通。"

用户说的收件箱是**每个 agent 一条对话线程的聚合视图**，而 DSH 的 todo 是一个单向通知板，没有回复字段。两者本质不同，无法复用。

**留下的教训**：同一个词，用户和我可能指两个东西。**先对齐指称，再讨论设计**。

### 2.7 被修正：主会话与收件箱的关系

一度把"主会话"和"收件箱"并列讨论，导致用户直接问：

> "我到底是在主会话里工作，还是在收件箱里工作？还是让主会话做收件箱？"

最终澄清为三层：

- **会话**：唯一的输入面，你在里面打字
- **收件箱**：选择去哪个会话的入口，不是工作区
- **主会话**：收件箱里第一行（root agent 那条），只在需要改结构/改规则/谈全局时才去

**留下的教训**：把不同抽象层的东西并列，会制造假问题。

## 3. 收敛路径

### 3.1 沟通：从"要不要限流"到"请示 vs 反馈"

关键突破是用户给出的这个区分：

> 向上级反馈是直接面向交代的任务本身的，而向我请示是长期规范性的。

它一次性解决了两个问题：

1. **准入规则**：什么该进收件箱（长期规范性），什么不该（任务级）
2. **稀疏化机制**：条目密度 ∝ 新增规范性决策的速度，而规范性知识只增不减 → 打扰自然单调递减，不需要额外设计

### 3.2 组织：从"总指挥"到"HRD + 研发总监"

角色演变：总指挥 → 研发总监（改名，因为"总指挥"和项目经理的职责重叠）→ root 改为 HRD。

一个关键判断被反复推演：**root 该叫什么**。试过"幕僚长"（被否："太难听"）、"COO"（被指出"高估权能，它会想拍板"），最后落在 **HRD**——因为 root 唯一真实的结构性特权就是组织权（看全树、建/撤人、改编制），这正是人事负责人的权域，不会诱发越权。

### 3.3 权限：从"命令"到"约束"

多线汇报一度看起来不可能，因为 DSH 的树是单亲结构。但它其实可行，只是要区分四种关系：

| 关系 | 机制 | 能否多线 |
|---|---|---|
| 创建/生命周期 | 单亲树 | 否 |
| 指导/派活/通知 | 消息（树内全连通） | 是 |
| 任务归属 | 共享任务板 | 是 |
| 打断/否决 | 祖先权限 | 否 |

于是确立：**直系上级能派活、能打断；非上级对接人只能提约束**。

### 3.4 并发：从锁到隔离

见 2.5。最终形成完整的代码流转链路：

```
建任务 → 分配槽位 → 重置主干 → 设计 → spec 审批 → 写码 → 本地自测
→ push → 研发总监评审合入 → 销毁实例 → 正式测试 → 校验 → 规范判定
```

其中三个细节是用户补充的、我原本没想到的：

- **spec 前置**：写码前必须产出 spec 交研发总监审批，且 spec 存档——它后来成了修复执行者的关键上下文
- **先合入再正式测试**：合入只要求本地自测通过；正式测试失败则 **feature 冻结、fix 开通**
- **失败不原地修**：新建修复执行者，带四样上下文（任务卡片 / spec / 失败报告 / 相关 diff）

### 3.5 上下文：从共享假设到隔离事实

我一度以为"DSH 不支持上下级之间的上下文切分"，用户直接质疑。核查后发现**恰好相反**：DSH 默认就隔离，父代只收结论，收不到子代的完整对话、工具输出和推理。

这引出一个重要推论：**结论质量是唯一的跨 agent 带宽**。所以条目格式、spec、报告的强制格式不是形式主义，是唯一的传输通道。

## 4. 未采纳的替代方案

| 方案 | 为什么没选 |
|---|---|
| 主会话做收件箱（所有请示汇总到 root 转述） | 每个字过两遍手，成本翻倍；我和 agent 之间永远隔一层 |
| 独立 Web 看板 | 等于造一个 Web 应用，与"先用侧边栏"的取向冲突 |
| 新增专职巡检节点 | 树里只有 root 能看全树，而 root 就是主会话；让插件当"眼睛"更便宜 |
| 全员常驻 | 9 个角色常驻对单人项目制造大量空转与互相请示 |
| 收件箱限流 | 与"前期愿意被淹没"直接冲突 |

## 5. 待验证的假设

这些是设计推演出的判断，还没有数据：

1. **研发总监会不会成为单点瓶颈**——它串行承担拆解、spec 审批、评审、合入、解冲突。按 10 分钟任务粒度推算，它每小时要处理约 18 次往返，很可能先堵。
   **处理方式**：先跑一周，交 HR 用真实数据评估。
2. **10 分钟任务粒度是否可行**——任务越小，重建成本占比越高。若任务卡片写得不够准，10 分钟任务会退化成 10 分钟读代码。
3. **一次巡检验否足够**——进入全面暂停后只允许一次巡检，重排后仍全阻就直接静默。可能过早放弃。
4. **"第二次不表态就走业界常规"是否够**——这个阈值是拍出来的。

## 6. 方法论上的一点记录

整个过程里，最有效的提问方式不是"你觉得怎么做"，而是：

- **"这个列表到底要不要独立开发插件？"**（逼出实现边界的判断）
- **"主会话到底做什么？"**（逼出抽象层的澄清）
- **"DSH 里 agent 的上下级关系是什么？"**（先要事实，再谈设计）

以及一条被反复验证的：**用户的"不要着急"通常是对的**——需求阶段每多花一小时澄清，实现阶段少返工一天。
