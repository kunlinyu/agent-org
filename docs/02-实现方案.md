# agent-org 基于 DSH 的实现方案（单方面意见）

> 本文是 TraeCode 使用 Kimi-K3.1-Pro 提出的单方面实现意见，不代表项目所有者已经确认的设计决策，也不构成需求基线变更。
>
> 依据：DSH commit `2e39e70496aa02986ca6a820c5d497e816b69d7e` 的源码与包文档。尚未进行运行时验证。

我的核心判断是：**不要把 agent-org 做成另一套多智能体平台，也不要 fork DSH；应该把它做成 DSH 之上的“组织领域层”。**

具体来说，建议采用 **“DSH 原生机制 + 一个 agent-org bundle + 少量领域模块”**。DSH 负责会话、消息、工具和持久化，agent-org 负责组织规则，不复制 DSH 已有的运行时。

## 一、能力边界这样划分

| 需求 | DSH 可以直接承担 | agent-org 需要补充 |
|---|---|---|
| 组织与会话 | 持续子 Session、`sendMessage`、`subagents/prompt`、`ui-subagent` | 固定组织树、角色关系、执行者生命周期 |
| 任务协作 | Agent Team 的 owner、依赖、claim、CAS revision、writeScopes | 业务状态机、角色权限、完整任务卡片 |
| 用户请示 | Session 事件日志、子会话续接、UI 扩展槽位 | 结构化请示、全局待办、回复关联、未读与等待时长 |
| 代码隔离 | 实验性 worktree、工作目录和沙箱机制 | 自动建删 worktree、Git 授权、spec 门禁、合入流程 |
| 模型分档 | `agentPreset`、`modelSelection`、`tokenUsage` | T1–T4 规则、升档校验、价格统计 |
| 业务监控 | `running` / `inactive` 等运行状态、Projection | `blocked` / `waitingUser` / `done` 等业务状态 |
| 定时巡检 | Cordis 宿主侧定时能力 | 给指定子角色投递巡检消息 |

**核心原则是：原生机制负责“能不能通信”，领域层负责“组织上允不允许”。**

## 二、组织树必须由代码创建，不能靠提示词

我不建议让 HRD 根据系统提示词自行创建所有角色。模型可能漏建、重复建或者认错上下级。

应该由 `org-runtime` 在启动时确定性地完成：

1. HRD 对应 root，沿用 DSH 固定的 `lead`。
2. 按需求中的汇报树创建长期角色。
3. 为每个角色绑定独立 `agentPreset`、默认模型档位和组织工具。
4. 执行者按任务动态创建，结束后 dispose。
5. 组织关系写入配置和事件，而不是只存在于 prompt。

还要特别处理 DSH 的 agent 名称限制：**逻辑槽位和真实实例名必须分开**。

例如：

- 逻辑槽位：`executor-1`
- 实际实例：`executor-20261120-0007`

DSH 名称不能随意复用，所以不能每次都在同一个 `executor-1` 上重建执行者。显示给用户的可以是槽位，消息路由使用真实实例 ID。

原生 `spawn_agent`、`send_message` 等工具也不应直接开放给所有角色，而是包装成：

- `org_assign_task`
- `org_spawn_executor`
- `org_report_parent`
- `org_request_user`
- `org_update_task`

这样在工具执行时强制检查“直属上级、对接人、优先级权限”，而不是希望模型自觉遵守提示词。

## 三、“请示”是最需要自研的部分

这里不能直接使用 DSH 的 `ask_user_question`：**存活的 delegated 子 agent 调用它会被 `DELEGATED_CALLER` 拒绝。**

我建议实现一套很轻量的结构化协议。

### 发起请示

角色调用 `org_request_user`，写入自定义事件，例如：

- `requestId`
- `originSessionId`
- `taskId`
- `summary`
- `options`
- `blocking`
- `createdAt`

事件统一进入组织树根 Session 的事件流，由 Projection 派生全组织的待处理请示。

### 展示与回复

- 用 `sidebar.panellist` 增加“待我裁决”，显示数量和等待时长。
- 点击后复用 `ui-subagent` 打开发起请示的子会话。
- 用户点击快速选项或提交回答时：
  1. 写入 `OrgRequestAnswered(requestId, answer)`。
  2. 调用原生 `subagents/prompt` 把回答发回原 agent。
  3. 原 agent 因新输入立即开始轮次。

只有仍处于 `pending` 的 `requestId` 才能完成回答，避免重复点击、重复唤醒。

**不要通过自然语言判断“这条消息是不是回答”。** 普通聊天就是普通聊天，只有通过明确的回答动作才关闭请示。

未读、等待时长也不需要另一套数据库：

- 待处理：有 `Requested`，没有 `Answered/Cancelled`
- 等待时长：`now - createdAt`
- 未读：最后相关事件晚于用户 read cursor
- 业务阻塞：存在 blocking 请示或未满足依赖

### 深谈建议后置

如果实现深谈，我倾向于使用 `subagent_fork`，并标记为 `discussionOf=requestId`：

- 保留在同一组织树内，可以继续使用原生消息和子会话 UI。
- discussion 节点不参与业务汇报树。
- 禁止再派生执行者。
- 结束时只允许把结论回填原会话。

普通 Session fork 会成为独立树，还需要额外解决来源追踪和跨树结论回传，不划算。第一版可以先只做“快速回答”。

## 四、任务板和 Git 不要重复保存同一份信息

建议以 `taskId` 贯穿全流程，但明确数据边界：

**Agent Team 保存实时协调信息：**

- owner / claim
- 依赖关系
- revision
- writeScopes
- 临时协调状态

**项目 Git 保存长期业务事实：**

- 完整任务卡片
- spec 及审批记录
- 自测、正式测试、校验报告
- 规范判定
- 最终交付记录

不要同时在 Team 和 Git 中维护两份完整任务状态，否则很快会出现一致性问题。

另外，DSH 的 `list_agents` 状态不能直接承担业务状态。保留：

- `running/inactive`：引擎是否正在运行
- `blocked/waitingUser/done`：由组织事件 Projection 得出

两套语义分开，反而更清晰。

## 五、worktree 和 spec 门禁由宿主控制

不要把原生 `enter_worktree` 直接交给执行者随意操作。推荐流程是：

1. `org-runtime` 为执行者创建 worktree。
2. 设置其 Session 工作目录。
3. 由宿主处理 linked worktree 提交所需的主仓库 Git 目录写授权。
4. spec 未批准前，通过 `tools/*` waterfall 拦截一般写文件和编码工具。
5. 执行者只能通过 `org_submit_spec` 提交指定位置的 spec。
6. 审批事件出现后，才开放编码能力。
7. 本地自测通过后提交，由组织流程负责合入。
8. 合入后依次执行正式测试、校验、规范判定。

如果正式测试失败，按现有需求创建新的修复执行者，而不是让原执行者不断修补并膨胀上下文。

worktree 目前仍是 DSH 的实验能力，尤其要优先验证：

- worktree 内能否正常 commit
- 主仓库 `.git` 授权是否足够
- Session 恢复后目录是否正确
- Windows 额外目录授权限制是否影响目标平台

## 六、巡检、暂停和模型分档都应集中控制

### 巡检

不要把原生 Schedule 直接绑定到子角色，它对 delegated Session 有限制。

更合适的方式是：

- 宿主侧 Cordis timer 触发。
- `org-runtime` 找到目标角色。
- 通过 `sendMessage` 投递巡检指令。
- 巡检结果写组织事件。

### 全面暂停

由 root 的领域控制器统一协调：

1. 写入 `OrgPauseRequested`。
2. 通过宿主侧用户级控制中断所有活跃成员。
3. Projection 派生 `pausing`。
4. 全部安静后执行一次巡检。
5. 写入最终 `paused` 状态。

不要让每个 agent 自己决定“组织是否已经暂停”。

### 模型分档

角色 preset 保存默认档位，创建执行者时通过 `modelSelection/agentOptions` 选择完整模型配置。升档必须由领域工具校验，不能让执行者任意选择昂贵模型。

`tokenUsage/contextPressure` 可以复用，但：

- 50% 上下文阈值只能按 DSH 的估算值执行。
- 成本需要自己的 provider/model 价格表。
- 执行者接近阈值时完成任务收尾并释放，不要依赖模型主动节省上下文。

## 七、实施顺序：先打通一条纵向闭环

不要一开始实现全部角色、所有 UI 和完整异常体系。

### 第一阶段：证明核心机制可行

打通：

**HRD → 研发总监 → 一个执行者 → 校验者**

同时包含：

- 确定性组织启动
- 一个结构化请示及用户回复
- spec 审批门禁
- 一个独立 worktree
- 自测 → 合入 → 正式测试 → 校验
- 一次性执行者释放
- 全局暂停

这一步能暴露绝大多数架构问题。

### 第二阶段：扩展协调能力

- 多执行者及依赖
- Team 任务板完整接入
- 业务状态 Projection
- 未读、等待时长、任务总览
- T1–T4 和成本统计
- 定时巡检、暂停后巡检

### 第三阶段：补增强能力

- 深谈 fork
- 邮件等外部通知
- 备份恢复
- 跨项目复用

## 最终判断

这个项目最重要的不是“创建很多 agent”，而是建立一层**可执行的组织规则**：

- DSH 的 Session 和 subagent 是通信底座。
- Agent Team 是协调工具，不是完整任务系统。
- Projection 是业务状态来源，不另建运行状态副本。
- Git 是长期事实载体。
- 工具拦截和宿主生命周期管理负责真正落实规则。

同时建议锁定 DSH 版本，并通过适配层和契约测试隔离其 developer preview 阶段的破坏性变更。以上结论来自对指定 commit 的源码和包文档审查，尚未做运行时验证；最优先应验证的是**子角色请示回复、worktree 内提交、执行者唯一名称与容量清理**这三个点。
