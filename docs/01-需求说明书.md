# 多 Agent 开发框架 · 需求说明书 v1.3

> 文档性质：需求描述（不涉及实现方案）
> 状态：需求基线，待进入实现阶段
> 日期：2026-11-28

---

## 1. 背景与目标

### 1.1 背景

我是唯一用户。我要像老板一样，指挥一支 AI 团队开发复杂项目，并在充分沟通的前提下让系统连续数天自主推进。

### 1.2 目标

| 编号 | 需求 |
|---|---|
| G-1 | 在 DSH 之上构建多 agent 开发框架，只服务我一个人 |
| G-2 | 支持任意类型的复杂项目，**一次只做一个项目** |
| G-3 | 前期接受高频打扰；共识稳固后打扰自然稀疏，可长期脱离运行 |
| G-4 | 项目严格按我的想法推进，所有关键决策经我放行 |
| G-5 | 每跑完一个项目，团队规范更厚一层，下个项目 warmup 更短 |

### 1.3 非目标

- 不做多人协作、多租户、权限体系、SaaS 化
- 不自建独立 Web 看板
- 不追求 agent 自主性最大化；优先可解释、可控、可回溯

---

## 2. 范围

**包含**：组织与角色、沟通链路、任务与代码流转、上下文策略、验收与报告、共识沉淀、异常兜底、监控与成本、安全边界。

**不包含（本版）**：多项目并行、跨项目团队复用流程、初始规范内容、插件实现方案。

## 3. 术语

| 术语 | 含义 |
|---|---|
| **请示** | agent 向我提出的、涉及长期规范性问题的请求 |
| **反馈** | agent 向直属上级汇报的、只影响当前任务的事项 |
| **收件箱** | 我与每个 agent 的一对一交流通道集合，按会话线程组织 |
| **槽位** | 一个执行者并发位置，持有独立的代码拷贝 |
| **spec** | 执行者在写码前产出的简短设计说明 |
| **规则卡片** | 一行一条的长期共识记录 |
| **全面暂停** | 所有 agent 都不处于 running 的状态（派生值） |

## 4. 组织需求

### 4.1 结构

| 编号 | 需求 |
|---|---|
| ORG-1 | 组织为**单一树**：HRD 为根，下辖研发总监、项目经理、产品经理、规范检察员、HR |
| ORG-2 | 研发总监下辖：架构师、执行者 ×3、校验者、运行测试员 |
| ORG-3 | 每个 agent 有**唯一一个直系上级**，以及**多个非上级对接人** |
| ORG-4 | 直系上级由「创建关系」决定，不靠组织图约定 |

### 4.2 权限

| 编号 | 需求 |
|---|---|
| ORG-5 | 直系上级可：派活、调整优先级、打断、接收完成通知 |
| ORG-6 | 非上级对接人只能提供约束、要求、反馈；**不得派活、不得打断** |
| ORG-7 | 任务分配只走共享任务板，执行者自行认领；**改派权只在 root** |
| ORG-8 | 冲突仲裁序：`产品验收 > 架构约束 > 任务排期 > 实现细节` |
| ORG-9 | root 是超级节点（唯一能看全树、能打断任何 agent），必须限制：能打断但不该随意打断，能看全局但不该随意介入 |

### 4.3 角色职责

| 角色 | 职责 | 触发 |
|---|---|---|
| HRD（root，主会话） | 组织中枢、路由中枢、全局状态、成本 | 常驻，沟通频率低 |
| 研发总监 | 任务拆解、派活、spec 审批、评审合入、槽位管理 | 常驻，**不写代码** |
| 项目经理 | 排期、milestone、进度维护、巡检、审计汇报 | 常驻 |
| 产品经理 | 需求、优先级、验收标准、验收报告 | 需求期高强度 |
| 架构师 | 架构方案、接口约定、技术选型、现状梳理 | 预研期高强度 |
| 执行者 ×3 | 并发执行槽位，写码交付 | 按任务创建，任务结束销毁 |
| 校验者 | 代码质量与风险结论 | 交付闸门 |
| 运行测试员 | 测试报告（硬性判据） | 交付闸门 |
| 规范检察员 | 按预定义标准判定合规 | 交付闸门 |
| HR | 组织诊断、成本统计、审计汇报 | 30 分钟巡检 + 暂停后分析 |

### 4.4 对接关系

| 编号 | 需求 |
|---|---|
| ORG-10 | 研发总监及其全部下属，均与项目经理、产品经理直接对接 |
| ORG-11 | 执行者与架构师对接（架构约束）、与运行测试员对接（测试反馈） |
| ORG-12 | 规范检察员与 HR **只与 HRD 对接**，监控所有 agent 但不直接与业务 agent 通信 |

### 4.5 组织调整

| 编号 | 需求 |
|---|---|
| ORG-13 | 组织结构可动态调整：我可直接以自然语言交代，或经 HR/HRD 的建议、在我于收件箱回复批准后生效 |
| ORG-14 | 调整内容包括：为某岗位增加人手；新增岗位（含职责描述）。调整前系统须以**固定格式**回显待生效变更，经我确认后才执行 |

### 4.6 工具集控制

| 编号 | 需求 |
|---|---|
| ORG-15 | 每个 agent 可调用的工具集可精确控制：配置落在项目 git（org/tools.yml，role→工具白名单），我可经自然语言提出要求后，对该岗位增删改查工具授权 |

## 5. 沟通需求

### 5.1 请求分两类

| 编号 | 需求 |
|---|---|
| COM-1 | **请示**给我：长期规范性问题，走收件箱 |
| COM-2 | **反馈**给直属上级：只影响当前任务的事，不进收件箱 |
| COM-3 | 判定问句：只影响当前任务→反馈；会成为以后同类问题的依据→请示 |
| COM-4 | 所有 agent 都可直接向我请示，不经上级转发 |

### 5.2 收件箱

| 编号 | 需求 |
|---|---|
| COM-5 | 收件箱是**会话聚合视图**：每个 agent 一条线程，通信走原生会话消息 |
| COM-6 | **不复用** DSH 的 todo 收件箱（它是单向通知板，无回复通道） |
| COM-7 | 侧边栏呈现：每个 agent 一行，带未读/待处理标记；点一行即进入该线程 |
| COM-8 | 默认只显示对话，执行过程可展开 |
| COM-9 | 三种处理：点选回复、展开追问、深谈（fork 议事会话） |
| COM-10 | 深谈不在原线程进行，谈完**只把结论回填** |

### 5.3 条目格式

| 编号 | 需求 |
|---|---|
| COM-11 | agent 对我发言必须遵循固定格式：结论 / 需要我回答的一个选择题 / 建议 / 可逆性 / 来源 |
| COM-12 | **一条只问一个问题** |

### 5.4 结论回流

| 编号 | 需求 |
|---|---|
| COM-13 | 我的裁决立即唤醒对应 agent 继续运行 |
| COM-14 | 不需要我催，不需要我手动去会话里再说一遍 |

### 5.5 合并

| 编号 | 需求 |
|---|---|
| COM-15 | 只有「我的一次回答能同时满足它们」时才合并 |
| COM-16 | 拿不准就不合并；错合并的代价远大于漏合并 |
| COM-17 | 合并须给出成员列表与理由；原始条目保留、可回溯 |

## 6. 任务与代码流转需求

### 6.1 计划闭环

| 编号 | 需求 |
|---|---|
| DEV-1 | 流程：需求（产品经理）→ 工作任务拆分（研发总监）→ 子任务 + 工时（执行者）→ 排期 + milestone（项目经理）→ 交付验收 |
| DEV-2 | **工时只由执行者给**（单位：分钟）；项目经理只汇总，不估算 |
| DEV-3 | **优先级只由产品经理给**；项目经理不发明优先级 |
| DEV-4 | 只在**关键 milestone** 做产品交付验收，不是每个任务都验收 |

### 6.2 项目起点

| 编号 | 需求 |
|---|---|
| DEV-5 | 支持**空白项目**起步（产品经理负荷最大） |
| DEV-6 | 支持**半截项目**接手：研发总监派架构师与执行者做现状梳理，产出架构认知后再定方向 |

### 6.3 代码隔离

| 编号 | 需求 |
|---|---|
| DEV-7 | 每个执行者槽位持有**完全独立的代码拷贝** |
| DEV-8 | 槽位在新任务开始前**重置到主干**；实例销毁后目录保留，可复用 |
| DEV-9 | **不使用写锁**；研发总监只做子目录级任务声明，防止两个槽位做同一块活 |
| DEV-10 | 编码纪律：先 fetch、再 rebase、再改动、**尽快推送**，不长持分支 |

### 6.4 前置 spec

| 编号 | 需求 |
|---|---|
| DEV-11 | 执行者写码前必须产出简短 spec，**交研发总监审批；批准后才能写码** |
| DEV-12 | spec 存档进项目仓库（按任务 ID），既作修复上下文，也作项目知识 |

### 6.5 合入与验证

| 编号 | 需求 |
|---|---|
| DEV-13 | 验证顺序：**本地自测 → 合入 → 正式测试 → 校验 → 规范判定** |
| DEV-14 | 合入前只要求本地自测通过，不要求正式测试通过 |
| DEV-15 | 研发总监评审并合入；冲突简单则自行解决，复杂则打回执行者 |
| DEV-16 | **推送并合入成功后才销毁执行者实例**，否则改动会丢 |
| DEV-17 | 合入后正式测试失败 → **冻结 feature 合入，fix 通道保持开通**；测试全绿后解除 |
| DEV-18 | 失败不原地修，**新建修复执行者**（原实例已销毁） |

### 6.6 失败处理

| 编号 | 需求 |
|---|---|
| DEV-19 | **同一任务连续 3 次失败** → 进收件箱，等我裁决 |

## 7. 上下文需求

| 编号 | 需求 |
|---|---|
| CTX-1 | 任务拆解必须保证**一个完整任务能在上下文内做完** |
| CTX-2 | 兜底：允许一次压缩后完成；仍不行则触发 HR 汇报（视为组织问题） |
| CTX-3 | **执行者是一次性实例**：任务结束即销毁，下个任务完全重建 |
| CTX-4 | 任务卡片必须**自包含**：任务 ID、目标、验收标准、涉及子目录、依赖任务、相关共识规则、适用规范片段、现状摘要 |
| CTX-5 | 粒度目标：工时约 **10 分钟**，上下文占用 **≤ 50%** |
| CTX-6 | 角色间上下文**原生隔离**，只传结论——因此结论质量是唯一带宽，格式必须强制 |
| CTX-7 | 修复执行者的上下文固定四样：原任务卡片、spec、失败报告原文、失败涉及的 diff hunk |

## 8. 难度与模型需求

| 编号 | 需求 |
|---|---|
| MOD-1 | 任务分 T1–T4 四档，档位决定模型与推理强度 |
| MOD-2 | 最终档位 = clamp(基础档 + 全局平移 + 执行者自提, 1, 4) |
| MOD-3 | 基础档由派活者标注；全局平移由我控制；执行者**只能上提一层**，不可降 |

## 9. 验收与报告需求

| 编号 | 需求 |
|---|---|
| ACC-1 | 硬性标准 = 测试员测试结果；交付物为**测试报告** |
| ACC-2 | 软性标准 = 产品需求；交付物为**验收报告** |
| ACC-3 | 质量与风险由校验者给出结论，不判功能对错 |
| ACC-4 | 边界：测试员不评需求，产品经理不评代码质量，校验者不判功能对错 |
| ACC-5 | 报告全文存项目 git；**邮件只放摘要 + 仓库链接**；同时可见于主会话 |
| ACC-6 | 以下必须我放行：需求基线、架构方案、执行规程中的规范、关键 milestone 交付验收 |

## 10. 共识需求

| 编号 | 需求 |
|---|---|
| CNS-1 | 触发记录：同类决策重复第 **2** 次 |
| CNS-2 | 触发强谈：与已有共识**冲突**时强制展开密集交互，不允许快速点掉 |
| CNS-3 | 触发记录：出现「以后都…」「一律…」等泛化表述 |
| CNS-4 | 不可逆或花钱的决定一律转待确认，**不得自动通过** |
| CNS-5 | 记录形式为规则卡片，一行一条，带编号、作用域、日期、来源 |
| CNS-6 | 共识**可废止**；冲突时须讨论，新规则须保持向后兼容或明确标注破坏性变更 |
| CNS-7 | 作用域默认项目内；经我放行后可沉淀到团队规范仓库 |

## 11. 异常与兜底需求

| 编号 | 需求 |
|---|---|
| EX-1 | 我离线时系统逐渐停，接受；我回来后逐条恢复 |
| EX-2 | 我不表态：持续提醒我表态；**所有请示必须由我答复，不自动默认执行** |
| EX-3 | **人人可反驳我**，依据必须是行业共识或公开资料；我坚持则我赢，但反驳意见**留档**，事后复盘重检 |
| EX-4 | 需求变更：我口述 → 产品经理整理文本 → **我确认最终文本** → 才传给架构师/研发总监/执行者。未确认的文本不得进入开发 |
| EX-5 | 全面暂停后执行**一次**巡检（延迟 10 分钟）：重排任务、语义合并、判定冷却；重排后仍全面暂停则彻底静默，不再巡检 |
| EX-6 | 巡检由**项目经理**执行；全局状态由监控插件注入，不依赖树查询 |
| EX-7 | 静默必须可见：显示待处理条数与最久等待时长 |

| OPS-2 | 监控插件同时展示项目执行进度，该进度**由项目经理维护** |

| OPS-5 | 停机走监控插件，不走邮件 |
| OPS-6 | 审计回看 = 项目经理的汇报 + HR 的汇报 |

## 17. 验收标准

| 编号 | 标准 |
|---|---|
| AC-1 | 真实项目连续推进 ≥ 3 天，无需重新交代背景 |
| AC-2 | 全面暂停时能看到每个 agent 卡在哪一条 |
| AC-3 | 同一问题不会在未合并的情况下问两遍 |
| AC-4 | 我答两次的事会自动变成生效规则，并影响后续行为 |
| AC-5 | 我睡着时不可逆操作不会被偷偷执行 |
| AC-6 | 所有需求、架构、规范、报告都经过我放行/审批 |
| AC-7 | 每完成一个项目，团队规范仓库有可复用增量 |
| AC-8 | 成本可估算、无异常空转 |
